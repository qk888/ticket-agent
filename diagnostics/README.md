# diagnostics —— 一次性排查脚本

这里放的是**当时为了回答某一个具体问题而写的脚本**：每条只答一问，
答案已经写进 `../README.md` §4.2 的缺陷取证链里。
脚本本身留着当**证据**（README 里写着「实测依据 `_r10diag.py`」，
那个文件必须真的存在），但不该占仓库首页。

## 与根目录 `_*.py` 的分工

| 位置 | 放什么 | 判据 |
|---|---|---|
| 仓库根目录 `_*.py` | **可持续复跑**的体检链 | 被 README / 测试 / 其他脚本**精确引用**（完整文件名），或属于命名过的体检流程 |
| `diagnostics/` | **一次性排查** | 当时只答一问，结论已归档 |

## 怎么跑

```bash
# 从仓库根目录跑（推荐）—— 这些脚本多数用相对路径定位 eval_out/ data/ src/
cd ..                                 # 回到 ticket-agent/
python diagnostics/_r10diag.py        # 而不是 python _r10diag.py
```

★ 有 10 个脚本靠 **cwd** 而不是 `Path(__file__)` 定位项目根，
所以必须从仓库根目录跑。移动前已逐个标注（见 `_tidy_plan.py` 的预检输出）。

## 命名约定

保留 `_` 前缀是刻意的：它让「这是排查脚本，不是库代码」一眼可见，
也让 `git grep` 能一行区分交付物与过程物。
Python 的 import 机制本来就不会碰这些名字（没有 `__init__.py`、不构成包）。

## 分类速查

- `_*probe.py` / `_*diag.py` / `_vwhy*.py` —— 定向取证，每条只答一问
- `_*check.py` —— 已被根目录的正式体检链取代或补充
- `_fix*.py` / `_adddefect*.py` / `_doc_sync*.py` —— 修完即废的补丁与文档注入脚本
- `_b*.txt` —— 会话记录导出，不是交付物

**没有一个被删除。** 理由是 README 里的引用必须指向真实存在的文件 ——
引用失效比首页乱更糟。git 历史里也有，但「git 里有」和「clone 下来能看见」是两件事。
