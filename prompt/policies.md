# 售后政策（会被切块进知识库，供 query_policy 检索）

> 本文件是 agent 的**唯一政策依据**。agent 不得凭记忆作答，
> 所有判断必须能引用到下面某一条规则编号（R1–R14）。
>
> ★ 阈值口径：本文件出现的每一个数字都对应 `config.py` 里的一个配置项，
> 运行时可用环境变量覆盖。**改配置不改文本（或反过来）会让校验器立刻变红** ——
> 由 `tests/test_policy_consistency.py` 守着。目的是让「谁改了阈值」可被人复核，
> 而不是只存在于某个人的记忆里。

## R1：七天无理由退货
客户签收商品之日起 7 个自然日内（配置项 return_window_days），商品完好的，可申请无理由退货。

- 起算点是**签收时间**，不是下单时间，也不是发货时间。
- 超过期限的，不予无理由退货，但可协商其他方案（需转人工）。
- 订单状态为「已发货未签收」的，不适用本条，见 R3。
- 订单状态为「待付款」的，不存在退款概念。
- 计算天数必须调用 `days_since_signed` 工具，**不要自己心算日期**。

## R2：不支持七天无理由退货的类目
以下类目不支持七天无理由退货（词表见代码常量 NON_RETURNABLE_CATEGORIES）：

- **内衣**（含无痕内衣、家居服等贴身衣物）
- **定制类商品**（如刻字皮带、定制尺寸服装）
- **数字商品**（云存储卡、课程兑换码等虚拟商品，一经售出不可退）

上述类目在签收后**如有质量问题**，需走质量投诉流程并提供凭证，由人工审核，不走无理由退货。
判断类目必须调用 `list_order_items`，**订单主类目和商品明细类目都要检查**。

## R3：已发货未签收的处理
订单已发货但客户未签收时，**不得直接发起退款**。

正确动作是发起**物流拦截**（调用 `block_order`），拦截成功后订单状态变更为「已取消」，
再按取消流程处理。直接退款会导致货、款双失。

## R4：需要人工审批的情形
以下任一情形必须转人工审批（调用 `escalate_to_human`），**agent 不得自行处置**：

- 退款金额**超过 500 元**（配置项 refund_hitl_threshold_cny；价保退差额同样按此项判定）
- 客户**风险评分超过 0.7**（配置项 risk_score_hitl_threshold）
- 客户已被**列入黑名单**

判断前必须调用 `get_customer` 获取 risk_score 与 is_blacklisted。

## R5：退款次数限制
**同一订单最多只能退款一次**（配置项 max_refunds_per_order）。同一订单已有退款记录的，不得再次发起退款。

追加补偿必须转人工处理。判断前必须调用 `list_refunds_of_order`。

## R6：完全不支持退款的类目
**生鲜类商品不支持任何形式的退款**，包括质量问题（词表见代码常量 NON_REFUNDABLE_CATEGORIES，与 R2 词表互斥）。

收到生鲜商品投诉时，应致歉并转人工（`escalate_to_human`），由人工判断是否给予补偿。
注意：R6 优先级**高于** R4，生鲜类目直接转人工，不需要先比金额。

## R7：工单关闭规则
工单在处置完成后必须关闭，正确状态取决于处置结果：

| 处置结果 | 工单状态 | 说明 |
|---|---|---|
| 正常退款/拦截完成 | `resolved` | 已解决 |
| 诉求不成立（超时效、不支持类目且无质量问题） | `rejected` | 明确驳回 |
| 触发人工审批（R4/R5/R6） | `pending_human` | 等待人工 |
| 客户意图不清（不知道是哪个订单） | 保持 `open` | **必须反问澄清，不得擅自关单** |
| 信息不足（缺凭证 / 缺原因 / 缺金额 / 缺现价） | 保持 `open` | 调用 `ask_customer` 把待答问题落库，等待客户答复 |
| 七个售后动作完成 | `resolved` | 与退款线同样必须关闭 |

## R8：换货
签收且在**换货期 15 天**（配置项 exchange_window_days）内的，可申请换货。

- **同一订单最多换一次**（配置项 max_exchanges_per_order），已有换货记录需人工核实。
- 订单待付款、已取消的，无货可换，应驳回。
- 订单**尚未签收**的，在途货物换货需人工判断是拦截还是等签收拒收。
- 非质量问题不适用本条，走 R2 驳回。
- 质量类原因需提供凭证，凭证类型要求见「附则 B」。

## R9：补发
适用于少发/漏发、发错、破损、丢件四类情形，按 `request_cause` 判定：

- 订单待付款的，无货可补；已取消的，应说明情况并驳回。
- **同一订单最多补发一次**（配置项 max_reships_per_order），已有补发记录需人工核实是否重复索赔。
- 未说明缺什么/哪里破损时，**不得猜**，调用 `ask_customer` 追问。
- 原因落在质量/破损/发错/丢件时需提供凭证。

## R10：赔付
客户有实际损失且平台需赔付的，按金额受理：

- 订单待付款或已取消的，不存在可赔付的损失。
- **赔付上限 30 元**（配置项 max_compensation_cny）：超出即必须转人工，agent 不得自行赔付。
- 客户未报金额时，**不得估一个数**，必须调用 `ask_customer` 追问。
- 质量类原因需提供凭证。

## R11：价保
下单后在**价保期 15 天**（配置项 price_protect_window_days）内页面售价下降的，退还差额：

- 差额超过 refund_hitl_threshold_cny 的，按 R4 转人工。
- 售价不低于下单金额的，不存在降价，不受理。
- 订单缺少支付时间或当前售价的，不得估算，必须先核实。

## R12：开票
订单已支付且未开票的，可开具发票：

- 同一订单**不得重复开票**；如需重开走红冲重开流程，由人工处理。
- 待付款、已取消的订单不能开票。

## R13：修改收货地址
- 订单**尚未发货**的，受理修改收货地址。
- 已发货的，地址只能由承运商改派，需人工联系承运商。
- 已签收的，收货地址已无意义，应说明情况并驳回。

## R14：催单
- 订单已支付且未签收的，受理催单。
- **催单冷却 24 小时**（配置项 urge_cooldown_hours）：冷却期内重复催单不再受理。
- 已签收 / 已取消 / 待付款的，分别按已完结、无需催、先完成支付处理。

## 附则 A：七个售后动作
七个非退款售后动作全部落在同一个写工具 `submit_after_sales_action` 上，区别只在 `kind`：

★ **两套名字不一样，且必须一起读**：「动作」是 agent 判出来的结论（「我要去开票」），
「诉求」是写工具 `submit_after_sales_action` 的 `kind` 取值（「客户当初要的是开票」）。
7 个里有 4 个同名（exchange / reship / compensate / price_protect），另 3 个不同名：
issue_invoice→invoice、change_address→address_change、urge_logistics→urge。
代码里由 `_ACTION_TO_REQUEST` 这一张映射表负责转换，两列都在下表里，不要只记其中一列。

| 动作（agent 判出的结论） | 诉求（写工具 kind 取值） | 对应规则 |
|---|---|---|
| `exchange` 换货 | `exchange` | R8 |
| `reship` 补发 | `reship` | R9 |
| `compensate` 赔付 | `compensate` | R10 |
| `price_protect` 价保 | `price_protect` | R11 |
| `issue_invoice` 开票 | `invoice` | R12 |
| `change_address` 改址 | `address_change` | R13 |
| `urge_logistics` 催单 | `urge` | R14 |

★ 不拆成七个独立工具：拆了会让模型面对「该调哪个」的选择，而那个选择恰好就是政策判断本身。

## 附则 B：凭证要求
政策要求凭证的原因有四种：质量（quality）、破损（damaged）、发错（wrong_item）、丢件（lost）。

判定经 `mark_evidence_received` 落库，凭证类型走受控词表校验。判据一句话：
**凭证要能证明问题本身，不是证明「买过、聊过」**。

| 原因 | 可接受的凭证类型 |
|---|---|
| quality / damaged / wrong_item | photo、video、inspection_report |
| lost | tracking_proof、photo、video |

`chat_log` 与 `screenshot` 在任何一种原因下都只证明「有过这笔交易」，**一律拒收**。

## 附则 C：多轮澄清
政策里任何一处「信息不足」（R9 缺原因、R8/R9/R10 缺凭证、R10 缺金额、R11 缺现价）都走同一条路：

1. 调用 `ask_customer` 把待答问题写进工单 —— **不是写在回复文本里**：只写在文本里，审计查不到、下一轮也看不到；
2. 工单保持 `open`，不得擅自关单；
3. 客户答复到达后，系统从答复中确定性解析出缺失的原因/金额/凭证并落库，然后重新跑一遍规则。

## 附则 D：处置流程规范
1. 先调用 `get_ticket` 了解工单内容
2. 若工单**未关联订单**（order_id 为空）→ 调用 `list_orders_of_customer` 看候选，
   若候选超过 1 个，**必须反问客户确认是哪个订单**（调 `ask_customer`），不得猜测
3. 定位订单后，退款线调 `check_refund_eligibility`，售后线调 `check_after_sales_eligibility` 做规则判断（不要自己推）
4. 需要查政策时调用 `query_policy`，并引用命中的规则编号
5. 按判断结果执行动作：`create_refund` / `block_order` / `escalate_to_human` / `submit_after_sales_action`
6. 最后调用 `close_ticket` 关闭工单（除非在等客户答复）
