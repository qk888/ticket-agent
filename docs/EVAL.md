## 1. 只比终态（τ-bench 式）

**不看 agent 说了什么，只看数据库最后变成什么样。**

```
期望终态（golden）         实际终态（export_snapshot）
  ticket.status = resolved    ticket.status = open
  refunds = [(approved, …)]   refunds = []
  order.refund_count = 1      order.refund_count = 0
                └──────────── diff ────────────┘
                        有 diff = 这条 case 失败
```

```python
ORDER_FIELDS  = ("status", "refund_count", "amount", "category")
REFUND_FIELDS = ("status", "amount", "requires_human")
TICKET_FIELDS = ("status",)          # intent 只观测、不判定
```

退款记录做**多重集比较**，所以先退款后建单还是先建单后退款都算对 ——
不惩罚合理的路径差异，只惩罚结果错误和越权动作。

为什么只看终态：**散文可以被写得和结论一样漂亮，数据库不会。**
1200 次真模型运行里，agent 说的话几乎全都对；失败的那部分全部是
「判对了但没收尾」—— 只有终态比对抓得到这种东西。

`TICKET_FIELDS = ("status",)` 是唯一判定字段，其他列进 `TICKET_OBSERVED_FIELDS`
（只观察不判定）。拿 agent 控制不了的字段判分，等于每条 case 都注定失败（见 DEFECTS ③）。

## 2. 过程违规也独立记账

终态对但过程错，仍然记一条违规。四个探针：

| 探针 | 抓什么 |
|---|---|
| `refund_without_eligibility_check` | 没调资格判定就退款 |
| `refund_fresh_category` | 给不可退类目退款 |
| `close_ticket_without_action` | 直接关单没办事 |
| `reject_without_eligibility_check` | 没调资格判定就驳回（手算规则也违规） |

第四个补上了一个盲区：原探针只在真的退款后才检查规则调用，
于是「agent 心算规则、正确驳回」完全隐形 —— 结果对，过程不可复核。

**终态准确率和违规数是两条独立的轴。** 一个 agent 可以 100% 准确但每次都不查规则
（不可上线），也可以 0% 准确但每次都老实查（只是能力不够，好修）。

## 3. pass^k

同一条 case 连跑 k 次，**k 次全对才算过**。

```
pass^1 = 96.7%   →  单次成功率
pass^3 = 40.5%   →  三次都成功的概率
```

差距就是「不稳定」的量化。k=1 的 96.7% 听起来很好，
但你不敢把它部署到真会退钱的系统里 —— 每两次就有一次办错事。

## 4. rule_ceiling：诚实标注的对照组上界

scripted 基线直调 `rules.decide()`，而 golden 由同一套规则推导 —— 所以它是 **100%**。

这个 100% **不是模型成绩，是评分标准下的上界参考**。它证明的是：

- 评测链路是通的（golden 生成 → 跑 → 比对 → 报分 全链路无误）
- 规则引擎自身一致（没有「golden 说该退、工具层说不该退」的漂移）
- 判据不会把对的判成错的

把它当模型能力报出来，就是拿评分标准冒充考生答卷。

## 5. 故障注入：证明评测框架真能抓到错

如果评测只会给好学生打分，它没法证明自己能抓作弊。所以往模型里注入**已知的错**：

| 故障模型 | 偏离点 | 注入什么错 |
|---|---|---|
| `flaky` | 随机 | 随机跳过一步 |
| `overprivileged` | 权限 | 给不该有的工具 |
| `guesser` | 歧义 | 多订单时猜第一笔，不反问 |
| `lenient` | 规则 | 超期驳回改成退款 |
| `noncompliant` | 规则 | 该转人工时自行关单 |
| `lucky` | 资格 | 跳过资格工具，自己拼策略 |

**关键教训：总准确率低 ≠ 故障危害小，总准确率高 ≠ 探针失灵。**

`lenient` 只在 7/30 条 case 上有触发机会，所以总分只从 100% 掉到 76.7%；
但在这 7 条上 baseline 1.000 → fault 0.000 —— **在有触发机会时检出率 100%。**
所以必须用「机会数 + 条件准确率」做分母，不能只看总分。

## 6. 两臂消融

同一批 case 跑 `single`（一个 agent 全流程）和 `multi`（triage/resolver/verifier 三角色）。
200 case × k=3，每臂 600 run，同 seed 7 / customers 1000：

| | single | multi |
|---|---|---|
| pass^3 | **40.5%** | 27.5% |
| 单次准确率 | **45.8%** | 42.3% |
| 模型调用 | 2.77 | 5.22 |
| 工具调用 | 3.21 | 4.10 |
| **写操作** | **0.53** | **0.45** |
| 违规 | 0 | 0 |
| 平均延迟 | — | 55.2s |

难度分层（single）：L1 42.4% / L2 32.8% / **L3 89.3%**。
★ **L3 比 L1 高近 47 个点** —— agent 在简单 case 上更差，
因为它会去猜一个动作，而正确动作是「按规则直接办」。

**多花的钱几乎全在重复只读复核，写操作反而更少。** multi 是净负面的。

拆到条件上看更有意思：multi 赢的全是「该驳回 / 该催办」类，
single 赢的全是「该起第二个 agent 干活」类。
例外是 `UNPAID:reject` / `CANCELLED:reject` 本该属「该驳回」却站 single 边 ——
共同点是 **agent 一次工具都没调就下结论**。
「该驳回」不等于「可以不查」。

**但也别把它读成多智能体没用。** `ambiguous` 与 `CANCELLED:reject` 两臂打平，
掉分最狠的 `no_order` 恰恰最该起第二个 agent。负结果成因**不是「多智能体本身错」，
而是「那个该起作用的角色没起作用」** —— 改法是 verifier 升级成 repair loop。

## 8. 缺陷 ⑲ 修复后的定向重跑：verifier 还会漏吗

18 条曾失败的 case 重跑：**仍失败 3 条、漏放行 0 条、恢复通过 15/18。**

三条失败全是 `observed_action == none` 且 `verifier_passed == False`（如实报「没办成」）。

> ⚠️ 这 18 条是**困难子集**，不能和全量 81.7% 直接比；且这轮只有 k=1，**没有 pass^3 可言**。
> 它只证明「verifier 判据修准后不再放行零动作」，**没有**证明整体变好。

## 9. 扩样本后读数为什么下降

40 case → 200 case，single 从 90.0% 掉到 45.8%。

**掉的原因是覆盖度从 11 个条件升到 32 个**，不是模型变差了。
难度分层会抹平「考的是哪条规则」：`R1:reject` 与 `R3:block_logistics` 都是 L1，
但自然分布里 R1 占 40%、R3 只占 2.7% ——
**agent 把每条 R3 全错，总准确率也只掉 2.7 个点。**

所以报表必须同时按条件分层，不只看难度。
